# Plug in and press Teleop — design, 2026-10-27

Gavin should plug the arms into any USB sockets and press **Teleop**. The Lab finds the right arms, loads their measured settings, and waits for them to wake up. A normal start needs no rehearsal, port picker, calibration prompt, or checklist. If something needs attention, show one short instruction while keeping the engineering details behind **Details**. Agents own testing and deployment.

This supports goal P (repeatable operation) and A3 (correct gripper mapping): “If I go anywhere, I plug in, it just works.” The important limitation is that today's software identifies USB adapters, not physical arms. We must resolve that before claiming the complete promise; guessing from a saved robot name is unacceptable.

Design only: no hardware commands, code/config changes, service changes, commits or pushes were performed. This file is the sole intended write. Earlier reviews are evidence, not implementation authorization. Paths below are repository-relative; `LR/` means `.venv/lib/python3.12/site-packages/lerobot/`.

## 1. Find the endpoints on every connect

Make discovery part of the connection transaction, before the existing record-clean readiness gate (`makermodslab/sessions.py:933-956`). Missing saved paths must not disable the very Teleop action that can rediscover them. Enumerate descriptors again at every click and reconnect, on both macOS and Linux; never fall back to a stale `/dev` path after an identification failure.

Extend `makermodslab/usb_ports.py:27-89`, which already does descriptor-only VID/PID/serial matching, macOS tty/cu alias handling, and singleton matching for serial-less devices. `utils/config.py:990-995` applies this only to records carrying metadata; `:1118-1154` captures it only when saving. New Viscous discovery must work without re-saving old Linux records and must use the same resolver for legacy starts. Paths and Linux by-id links are current locators, never identity.

CANable: locate known VID/PID and USB serial (dry `207E37A55445`, waterproof `205038953846`); use that as a search hint, then identify the attached arm independently. A replacement adapter can carry a known arm after that independent check. Deduplicate aliases; reject duplicate serials and enumeration errors. No broad “open every serial port” scan.

Star/CH340: enumerate supported adapter descriptors regardless of socket/path; when there is exactly one candidate and one leader slot, resolve that endpoint only after all seven expected FashionStar IDs answer, within the commissioned connection boundary below. Multiple indistinguishable candidates remain ambiguous unless a verified leader fingerprint identifies the commissioned one. USB location is a hint, never a persistent binding. Unplugging an unrelated duplicate is the fallback action; swapping laptop sockets never requires setup. A generic CH340 can front unrelated equipment: VID/PID alone does not authorize sending UART bytes to it. Unattended probing requires a dedicated enrolled assembly; arbitrary serial equipment with identical descriptors needs an arm-attached serialized connection, not speculative pings.

## 2. Identify the arm, with an explicit protocol boundary

| Operation | What the evidence permits |
|---|---|
| USB descriptor enumeration | Passive; opens no serial/CAN device (`usb_ports.py:27-41`). Safe for background UI availability. |
| Existing CAN probes | **Not passive discovery.** `maker_ports.py:149-178` calls RobStride handshake/read; `:212-267` explicitly enables Damiao's pan motor. Never reuse these for automatic scans. |
| RobStride state/handshake | Sends standard frame `FF FF FF FF FF FF FF FB`, clearing faults (`LR/motors/robstride/robstride.py:227-236,288-318,932-955`; `tables.py:102-106`). No enable in that query, but a real state change; cached fallback also cannot prove fresh feedback. The reported change in hand feel is unresolved (`docs/viscous-mapping/README.md:143-150`). |
| Damiao handshake | Sends enable per motor (`LR/motors/damiao/damiao.py:223-251`). Exclude it entirely from waiting/discovery; do not retry `device.connect()` under a “read-only” label. |
| FashionStar ping/monitor | Queries `0x01`/`0x16`; no enable, fault-clear, origin or motion command. `fashionstar_raw.py:180-226` enforces an allowlist and validates replies. Do not instantiate the normal Star leader as a probe: `LR/teleoperators/rebot_102_leader/rebot_102_leader.py:232-241` unlocks and resets turn counters; button options can lock on connect (`:185-186`). Star servos are actuators, despite older comments describing an encoder-only arm. |

**Preferred follower identity:** ordered `(joint CAN ID, MCU UID)` for all seven motors, enrolled once and committed with the unit. A motor replacement changes the fingerprint and requires recommissioning; one matching base motor is insufficient. Query requests/replies need strict ID/type/length checks and bounded receive queues; never learn a new identity automatically from whichever device answers.

RobStride's [official sample](https://github.com/RobStride/Python_Sample/blob/main/robstride_dynamics/protocol.py) separates GET_DEVICE_ID (type 0) from enable, control and parameter writes. The [RS00 manufacturer manual](https://files.seeedstudio.com/products/RobStride/Product%20Literature/RS00/RS00User%20Manual251112.pdf), PDF pp.19–20, documents a private-protocol extended type-0 request with zero data and a 64-bit UID reply: passive by specification. **MIT-mode support is unproven.** Its pp.37–38 associate MCU replies with ID/protocol/host-ID modifications, not a passive MIT identity query. Never issue those writes, even “set the same ID,” to discover identity; never auto-switch protocols.

**Leader identity:** IDs 0–6 establish topology, not uniqueness. The [pinned FashionStar vendor SDK](https://github.com/servodevelop/servo-uart-rs485-sdk/blob/f72877669af0a4dc3501bb98df291cacc0a8592e/micro-python/src/uservo.py#L232) distinguishes read-data `3`, write-data `4`, and reset-user-data `2`; `:555-580` encodes a data read without a write. No verified spare persistent tag field or immutable UART servo UID has been established for these leaders. Do not repurpose servo IDs, origin, protection or other EEPROM settings. A manufacturer's CAN-servo serial-number table is not evidence for this UART hardware. Exact-model documentation plus a bounded read-only test must precede any proposed fingerprint field.

**Fallback decision:** exactly one candidate solves endpoint ambiguity, not physical identity. Without verified MCU/leader identity, enable only a commissioned, permanently arm-attached serialized adapter/harness whose reassignment requires maintenance; otherwise refuse torque. A loose adapter serial or a singleton generic Star alone cannot certify which unit/calibration is attached. If adapters must remain freely swappable and passive identity is unsupported, the full requirement needs an arm-bound identifier or a separately qualified driver/protocol change. This is a release gate, not a prompt Gavin must answer on each trip.

First containment: canonical adapter assignments must reject the existing Linux waterproof→dry binding before any device open. Final architecture resolves `fingerprint → physical unit → measured profile`; the selected record supplies preferences/cameras and an expected unit constraint, never identity. A stale waterproof selection with a dry fingerprint returns a mismatch before torque; the UI auto-selects the sole verified available pair for ordinary Teleop. Multiple verified pairs use their enrolled pairing and existing selected unit; do not guess which follower one leader should drive. Viscous remains single-pair (`arms/viscous.py:25,126-127`), not implicit bimanual control.

## 4. One cancellable connection transaction, every Teleop press

1. Claim the existing session/mutex and lease, then exclusive device ownership, including cooperation from bench scripts. Return the session ID/lease immediately in a starting phase and perform waiting in the session worker, so the UI can heartbeat/cancel without a 65-second blocked start request. Preserve registry dispatch and reciprocal busy checks (`CLAUDE.md:151,186`; `teleoperate.py:932-945`); no separate background poller competing for the bus. Stop, lease expiry and browser abandonment cancel waiting as well as running. External port holders produce a busy result; never kill them or force-close their devices.
2. Enumerate, resolve and verify unit/pair identities; validate bundle, frame and effective settings. Keep ownership through preflight and activation. Re-enumerate/reidentify after any disconnect, never resume torque automatically after hot unplug. Resolve before config staging so a wrong record cannot stage the wrong profile.
3. Open transport with `handshake=False`, **without** ordinary follower/leader `connect()`. Run audited non-energizing readiness queries and Star ping/monitor. The new pre-torque boundary must be mandatory even when no optional speed limiter was requested; current freshness enforcement is only in `can_speed_limit.py:83-119`.
4. Retry only absence/timeouts/temporary enumeration loss: immediate, 250 ms, 500 ms, then at most once per second; one shared **65 s** monotonic deadline includes every serial/CAN call. Bound each round to 500 ms, support cancellation within 250 ms, and never nest seven long per-motor retry budgets. Identity, fault, schema, ambiguity and drift failures are terminal, not retryable.
5. Show “Waiting for the arm to power up...” immediately; after 3 s of total follower silence show “Turn on the large arm’s power switch.” while continuing automatically. For Star silence use its separate instruction below. If it becomes ready at 5–60 s, finish that same click. At 65 s stop waiting, close handles, retain the instruction; no delayed surprise start after timeout/cancel. If both are silent, show one instruction at a time in connection order.
6. Require a fresh, validated response from **every** follower and Star joint, not cached positions: finite angle/velocity/temperature, valid IDs, healthy faults/voltage where available, temperatures below the profile's qualified ceiling, and timestamps from this attempt. Collect two complete sweeps; all samples must be ≤250 ms old immediately before activation, refreshing if necessary. A healthy target is ≤2 s to readiness (adapter-open delay included); measure this, do not advertise it as achieved. Startup synchronization can take longer and displays “Matching the arms...” without another click.
7. Apply only the profile's documented, uniquely resolvable whole-turn correction (`MakerFollower._detect_full_turn_offsets`, `:170-202`); +327.5→−32.5 is not a new zero. Check measured hard-stop envelopes with per-joint commissioned measurement tolerance (initial target 2°, to qualify), separately from inward soft limits. A pose just outside a soft limit but inside measured travel passes and starts from its actual position, preserving d28d5fc4. Never widen limits or recapture zeros automatically.
8. Check leader raw travel/unwrap, mapped target validity, and feasible bounded startup synchronization. Compare rest-pose residuals only against an **independently established** rest landmark/fixture or supported pose; arbitrary joint readings cannot prove that the physical arm is folded. No compulsory folding/rehearsal. An in-envelope slipped zero may remain undetectable without a physical reference: expose this limitation, and qualify mechanical retention/landmarks during commissioning. Move `_stale_zero` refusal ahead of all torque; do not use the old ±20° grace as evidence that zeros are correct.
9. Only after both sides pass, initialize each target at fresh actual motor coordinates and activate once, with the shared bounded startup/slew policy, including a qualified gripper startup cap (current limiter exempts it, `can_speed_limit.py:149-152`). Reuse existing return/release behavior for normal stop. Any activation exception releases **all** attempted motors even if `is_connected` is false; any release uncertainty stops retries and instructs power-off. Never release a device owned by another session.

**Readiness protocol gate:** the current `0xFB` position refresh is non-enabling but clears faults; it must not be silently called passive. The RS00 manual p.38 also documents a fault-only request using a non-`FF` command byte; qualify that without clearing faults. It does not by itself supply fresh positions. Before shipping, establish a passive fresh-position query on the actual firmware (or qualify a replacement transport); prohibit implicit fault clear and zero-gain “probe” motion packets. Until this and physical identity are solved, strict preflight must refuse rather than simulate readiness. No such validation was performed in this design task.

Waiting and partial readiness send **zero enable/target/configuration frames**; therefore partial handshake cannot leave motors energized. Never retry the existing Damiao handshake. A future Damiao implementation needs its own passive preflight; if any enable was attempted, existing `torque.de_energize_can_device` recovery must run before another attempt, and a failed recovery terminates. Software cannot guarantee torque-off after cable/power/control-process failure; the power switch remains the hard stop.

## 5. One plain sentence, with secondary technical details

Return stable `robot.*` codes plus English `detail` and structured `details` (unit, endpoint, missing joint, attempt/deadline, fault, expected/observed identity, profile/release hashes, cleanup result). Classify at the source, not by regex against the generic wrapper. The top-level sentence/status is the only prominent prose; **Details** expands the diagnosis, without raw exceptions appended to the instruction.

| Failure class / proposed code suffix | Exact prominent sentence |
|---|---|
| CAN adapter absent / `follower_usb_missing` | “Connect the large arm’s USB cable.” |
| Star adapter absent / `leader_usb_missing` | “Connect the small arm’s USB cable.” |
| CAN all silent after 3 s / `follower_not_ready` | “Turn on the large arm’s power switch.” |
| Star slow/silent / `leader_not_ready` | “Connect the small arm’s power supply.” |
| Some follower motors silent, stale/corrupt feedback / `feedback_missing` | “Reconnect the large arm’s power cable.” |
| Multiple indistinguishable adapters/pairs / `connection_ambiguous` | “Unplug the extra arm connection.” |
| Record expects another identified unit / `unit_mismatch` | “Select the connected arm shown above Teleop.” |
| Identity unsupported/unrecognised / `identity_unverified` | “Use the commissioned arm-and-cable set.” |
| Other session or external process holds port / `port_busy` | “Close the other arm session and press Teleop again.” |
| Leader outside measured travel / `leader_pose_invalid` | “Move the small arm into its normal travel range.” |
| Impossible follower pose, stale zero, failed rest landmark / `frame_mismatch` | “This arm’s alignment needs repair; use the other arm.” |
| Missing, mismatched or invalid profile / `profile_invalid` | “This arm’s saved setup needs repair; use the other arm.” |
| Overtemperature / `too_hot` | “Let the large arm cool down before pressing Teleop.” |

| Unknown exception / `connection_failed` | “Reconnect the arm’s USB and power cables, then press Teleop.” |

Silence cannot distinguish off, broken wiring and wrong protocol: the power instruction is a first action, not a claimed diagnosis. Persistent/repeated failure must retain details for agent repair rather than repeat retries indefinitely. Alignment/profile/identity repair cannot honestly be fixed in seconds at a visit; release qualification must eliminate the known cases, and those sentences are safe fallbacks for genuine faults, not successful fulfilment of the travel promise.

Follow `frontend/docs/localization.md:10-36`: backend prose stays English; translate client fallback/status labels in every catalog, preserving machine codes, IDs, phases, paths, requests and stored values. Use `ApiError.code/details` (`frontend/src/lib/apiClient.ts:6-15`) for decisions; never translate or parse backend strings. UI uses session phase/status refetches, with heartbeat during waiting; do not invent a browser safety owner. API/schema changes update OpenAPI and SDK/ratchet fixtures (`CLAUDE.md:139-151`).
